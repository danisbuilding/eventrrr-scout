# Handover: building Eventrrr Scout

For the chat that owns the Scout product and pipeline. The sorting/charter work has its own handover
(`docs/handover-sorting.md`) and its own chat; this doc is everything else. State as of 2026-11-02.

## What Scout is

A standalone tool at **https://scout.eventrrr.com** that sweeps public sources for Mexico City events, extracts
and dedupes them, scores highlights, and lets DP review, sort into curator profiles, and export batches into
Eventrrr (eventrrr.com, his Bolt.new app). DP is the only user; the login is Google, allow-listed.

Repo `danisbuilding/eventrrr-scout` (Claude GitHub app installed; add the repo with push access in a new chat).
Site is GitHub Pages from `site/` (custom domain via a `scout` CNAME on Spaceship; apex/www belong to Bolt, never
touch them). Data lives in the repo (`runs/`, `inbox/`, `profiles/`) and in Eventrrr's Supabase (decisions,
profiles, assignments).

## How a sweep runs (fully autonomous)

Runs tab → **Start sweep** (weeks ahead 1–8, optional name/umbrella, checkboxes: Websites always, Instagram on,
ChatGPT/Gemini off by default). The site calls the Supabase edge function `scout-trigger`, which fires a
`repository_dispatch` (type `sweep`) on `.github/workflows/pipeline.yml`:

| Stage | Code | Notes |
|---|---|---|
| Instagram | `scout/instagram_apify.py` | Apify `apify~instagram-scraper`, 18 posts/account, 21 days; ~$1/sweep |
| LLM scouts (opt-in) | `scouts/run_scouts.py` | OpenAI/Gemini web-search scouts in parallel; slow, off by default |
| Web | `scout/web_sweep.py` | requests + trafilatura + bs4 over `sources.yaml` sites and umbrella `known_pages` |
| Extract | `scout/extract.py` + `prompts/extract.md` | gpt-5-mini, low reasoning, 8 parallel batches (~$0.50/sweep); Gemini fallback; alias normalization for stray field names |
| Normalize | `scout/normalize.py` | fuzzy dedupe (token Jaccard ≥0.6, same day, years stripped) |
| Score | `scout/score.py` + `taxonomy.yaml` | signals/penalties, threshold 7 |
| Thumbs | `scout/thumbs.py` | flyer images |
| Publish | `scout/publish.py` | writes `runs/<run>/events.json`, updates `runs/index.json`, commits |

`runs/status.json` is written during the run; the Runs tab polls it and GitHub's public API. Inputs also include
`reuse_inbox` (re-extract without re-gathering). A concurrency group serializes runs.

Secrets (GitHub Actions): `APIFY_TOKEN`, `OPENAI_API_KEY`, `GEMINI_API_KEY`. Optional repo variables:
`OPENAI_EXTRACT_MODEL`, `OPENAI_EXTRACT_EFFORT`, `EXTRACT_WORKERS`, `SCOUT_WORKERS`. Edge function secret:
`GITHUB_SCOUT_TOKEN` (for dispatch and for committing to `sources.yaml`). Never ask for or paste any of these;
the Supabase anon key in `site/config.js` is public by design.

## The site

`site/index.html`, `app.js`, `styles.css` (Neue Verdant design system, `design/`), `config.js`, `categories.js`
(generated from `taxonomy.yaml`), `sources.json` (generated by `scout/export_sources.py`). supabase-js 2.45.4
UMD. Events are read from raw.githubusercontent.com; decisions/profiles/assignments from Supabase. An inline
mode (`window.SCOUT_INLINE`) renders a mock with `python scout/render.py <run>` for offline checks; to test the
real page, serve `site/` locally and inject `SCOUT_INLINE` with Playwright (pre-installed).

| Tab | What |
|---|---|
| Events | Per-run table, inspector, Keep/Skip, 140-char public note, tick rows → **Export to Eventrrr** (one JSON for N events), Copy decisions |
| Sort | All runs in one pool; profile chips per event (+None); event details in the right panel; profile panel (new/edit/archive, per-profile Export, charter display); **Copy session** |
| Sources | List + **Add source** (website/Instagram) with verification via the edge function, commits to `sources.yaml` |
| Runs | Start sweep form, live status, past runs |

Mobile: nav visible, sort rows stack into cards, side panels become full-screen sheets.

## Supabase (Bolt-managed; no dashboard access, everything goes through Bolt prompts)

Project `https://psqedmbyopememsqrynk.supabase.co`. Tables `scout_reviewers` (allow-list), `scout_runs`,
`scout_decisions`, `scout_profiles`, `scout_assignments`; function `scout_is_reviewer()` (email on the list AND
provider = google); RLS `for all to authenticated using/with check (scout_is_reviewer())` on every scout table.
Edge function `scout-trigger` (source in `supabase/functions/scout-trigger/index.ts`, deployed via Bolt).
SQL in `supabase/schema.sql` and `supabase/profiles.sql`. To change the DB: write the SQL, give DP a prompt to
paste into Bolt, ask for the output verbatim.

Gotcha found 2026-10-29: `upsert()` into `scout_profiles` fails RLS while plain `insert()` passes with the same
policy. Use insert/update, not upsert, on that table.

## Eventrrr side

Import contract in `docs/eventrrr-import-prompt.md` (`{"eventrrr_import":1, "events":[…]}`, max 100, whitelisted
fields, lands in Eventrrr's Inbox "To review"). Eventrrr has 12 categories (`taxonomy.yaml` mirrors them). Each
curator profile is a separate Eventrrr account; the profile's `handle` field records which.

## How DP works

Concise, tables, honest pushback, no obvious precautions. He refuses one-by-one manual steps (that's why export
is a batch JSON). Don't cancel or trigger his workflow runs without his say-so. He's technical (reads SQL, uses
DevTools) but has no direct Supabase access. He tests on mobile. When something breaks he sends a screenshot;
reproduce with Playwright before guessing.
